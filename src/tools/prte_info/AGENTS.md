# AGENTS.md — `src/tools/prte_info` (report the installation)

Orientation for `prte_info`, installed as `prte-info` with a legacy
symlink `prte_info`. Start with [`src/tools/AGENTS.md`](../AGENTS.md)
for what all the tools share.

---

## What it does

`prte_info` answers "what is this PRRTE, and what can it do". It is the
first thing a bug report should contain (`prte_info --all`), and it is
the only tool that touches no DVM and starts no runtime: it registers
every framework's MCA parameters so it can print them, and exits.

Almost all of the work is done by PMIx's `pmix_info_support` layer —
`pmix_info_show_version()`, `pmix_info_do_params()`,
`pmix_info_do_config()` and friends. This file's job is to build the two
arrays those functions walk:

- **`mca_types`** — the type names to report under: `mca`, `prte`,
  `hwloc`, `pmix`, `rml`, `routed`, plus every framework in
  `prte_frameworks[]` (generated by `autogen.pl`), plus the PMIx
  frameworks when `--include-pmix` is given. `rml` and `routed` are
  listed by hand because they are no longer frameworks but still have
  parameters.
- **`prte_component_map`** — filled by
  `pmix_info_register_project_frameworks()`, which opens every framework
  and records what components it found.

A new framework needs no change here; a new *non*-framework parameter
prefix does.

---

## Things worth knowing before you change it

- **`prte_register_params()` is idempotent** (it returns early on a
  second call), so the explicit call here is a no-op —
  `prte_init_util()` already made it. Harmless, but do not add logic to
  it expecting a second pass.
- **`--include-pmix` prints a second report** under its own banner. The
  two halves are near-copies of each other; when you change one, check
  the other. One of them showed the *PRRTE* component versions under the
  "PMIx CONFIGURATION" heading for exactly this reason.
- **`acted` decides whether the default report is printed.** Every
  branch that produces output must set it, or the tool prints its
  selective answer and then the whole default report as well.
- **`--version <framework>[:<component>]` is currently unreachable.**
  PMIx's `pmix_cmd_line_parse()` intercepts `-V`/`--version` itself and
  returns `PMIX_OPERATION_SUCCEEDED`, so the option never reaches the
  `PMIX_CLI_INFO_VERSION` handling in this file and `prte_info --version
  rmaps` just prints the tool's own version banner. Per-component
  versions are still reachable through the default and `--all` reports.
  Fixing this means changing where PMIx decides to intercept — do not
  work around it here by pre-scanning argv (see the "generic CLI code
  lives in PMIx" rule in the top-level [`AGENTS.md`](../../../AGENTS.md)).
- **This tool must never need a DVM**, must never open a socket, and must
  keep working in a tree that was configured with
  `--enable-testbuild-launchers` (where some components cannot `dlopen`).
  That is exactly what makes it useful in a bug report.

## Testing

There is nothing here to unit test — the tool is a sequence of calls into
PMIx's reporting layer — so it is covered by running it:

```sh
prte-info                 # default report
prte-info --all           # everything, incl. every MCA parameter
prte-info --include-pmix  # ...and the PMIx half
prte-info foo             # rejected: message plus exit 1
```

The multi-node suite in
[`contrib/dockerswarm/`](../../../contrib/dockerswarm/) runs it on every
node and compares the reported version, which is the cheapest way to
catch a swarm running a stale install — a failure mode that otherwise
shows up much later as an inexplicable launch error.
