[prte_init:startup:internal-failure]

It looks like "prte_init()" failed for some reason. There are many
reasons that can cause PRRTE to fail during "prte_init()", some of
which are due to configuration or environment problems.  This failure
appears to be an internal failure — here's some additional information
(which may only be relevant to a PRRTE developer):

   %s failed
   --> Returned value %s (%d) instead of PRTE_SUCCESS

is on the list of prohibited locations:

   Location given: %s
   Prohibited locations: %s

If you believe this is in error, please contact your system
administrator to have the list of prohibited locations changed.
Otherwise, please identify a different location to be used (use "-h"
to see the cmd line option), or simply let the system pick a default

[prte:session:dir:owner]

PRRTE found an existing directory at the location it uses for its
session directory, but that directory belongs to another user:

   Directory: %s
   Owner uid: %lu
   Our uid:   %lu

Session directory names are predictable, so a directory with the right
name and the wrong owner is either left over from another user's job
or was created to intercept this one. PRRTE will not use it. Remove the
directory (this may require the system administrator), or point PRRTE
at a private temporary directory (use "-h" to see the cmd line option).
#
[prte:session:dir:writable]

PRRTE found an existing directory at the location it uses for its
session directory, but other users are allowed to write to it:

   Directory: %s
   Mode:      %04o

PRRTE never creates its session directories that way, and other users
may already have placed files in it, so PRRTE will not use it. Remove
the directory and try again.
#

[bootstrap-duplicate-node]

Bootstrap startup was requested, but the configuration file lists the
same host more than once in DVMNodes:

   file:   %s
   host:   %s

A host's position in DVMNodes determines its rank in the DVM, and every
daemon computes its own rank from this same file. A repeated entry
therefore leaves a rank that no daemon will ever claim, and the DVM can
never finish forming.

Please list each host exactly once and try again.

[prte:session:dir:shared]

PRTE has detected that the head of the session directory tree (where
scratch files and shared memory backing storage will be placed)
resides on a shared file system:

   Directory: %s
   File system type: %s

For performance reasons, it is strongly recommended that the session
directory be located on a local file system. This can be controlled by
setting the system temporary directory to be used by PRTE using either
the TMPDIR envar or the "prte_tmpdir_base" MCA param.

If you need the temporary directory to be different on remote nodes
from the local one where %s is running (e.g., when a login node is
being employed), then you can set the local temporary directory using
the "prte_local_tmpdir_base" MCA param and the one to be used on all
other nodes using the "prte_remote_tmpdir_base" param.

This is only a warning advisory and your job will continue. You can
disable this warning in the future by setting the
"prte_silence_shared_fs" MCA param to "1".

[uniform-nodes-mismatch]
A node has reported hardware that differs from this node's:

  Node: %s

"--uniform-nodes" (or the prte_uniform_nodes MCA parameter) asserts that
every node of the allocation is identical, and PRRTE acts on that rather
than merely noting it: only one daemon is asked for its hardware, and every
other node is given what that one reported. The node above disagrees, so the
assertion does not hold and the other nodes have been described wrongly -
their processes would be placed and bound against hardware they do not have.

Remove the option and let PRRTE discover each node's hardware for itself.

[dvm-key-not-delivered]
A PRRTE daemon did not receive its DVM key:

  node:      %s
  expected:  %s
  problem:   %s

Every daemon of a DVM holds a key, created by the DVM controller
and delivered to each daemon as it is launched, and a daemon proves it
holds the key before any other daemon will talk to it. The key is never
put on a command line, where anything on the node could see it: the ssh
launcher writes it to the daemon's standard input, and the resource-manager
launchers (Slurm, LSF, PALS) pass it in the daemon's environment.

If the remote-launch agent in use does not forward standard input to the
command it runs, it cannot deliver the key. Use an agent that does (ssh,
rsh and "qrsh -inherit" all do), or launch through the resource manager.
As a last resort the check can be turned off with
"--prtemca prte_oob_authenticate 0" - but understand what that means:
daemons can then no longer tell their own peers from any other process
that connects to their ports.
#
[dvm-key-malformed]
A PRRTE daemon received a DVM key it cannot use:

  node:    %s
  source:  %s

A key is exactly 64 hexadecimal digits. This usually means something other
than the DVM controller wrote to the daemon's standard input or set the
variable - a login script that prints to its output, for example.
#
[dvm-key-file]
A PRRTE daemon could not read its DVM key from the file the bootstrap
configuration names in DVMKeyFile:

  node:    %s
  file:    %s
  problem: %s

Every daemon of a bootstrapped DVM must hold the same key, so that
daemons can prove to one another that they belong to the DVM. The file
must be a regular file (not a symbolic link) owned by the user the daemon
runs as, readable by no one else (mode 0600 or 0400), and contain exactly
64 hexadecimal digits. One way to create it:

  umask 077; head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n' > prte.key
#
[dvm-key-bootstrap-missing]
A bootstrapped PRRTE DVM was configured without a DVM key:

  node:   %s
  file:   %s

Every daemon of a DVM must prove to the others that it belongs to the
DVM, and in a bootstrapped DVM that proof is a key held in a file that
the configuration names with the DVMKeyFile entry. Create one, copy it to
every node (or place it on a file system they share), and add

  DVMKeyFile=<path to the key file>

to the configuration. The file must be a regular file owned by the user
the daemons run as, readable by no one else (mode 0600 or 0400), and hold
exactly 64 hexadecimal digits. One way to create it:

  umask 077; head -c 32 /dev/urandom | od -An -tx1 | tr -d ' \n' > prte.key
